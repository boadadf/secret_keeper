# ADR-001: Python orchestration with mitmproxy as the initial engine

Status: accepted for the first source delivery; packaging feasibility is a release gate.

Python is chosen to integrate with mitmproxy and later local detection libraries,
not because end users should install Python. TLS interception is delegated to a
maintained engine rather than implemented in-house. The initial adapter runs
mitmdump as a supervised child process and keeps configuration code independent
of engine imports. No custom addon or inspection policy is loaded yet.

A packaged launcher alone is insufficient: it must also ship the engine and its
native dependencies. Evaluate a licensed, version-pinned standalone engine bundle
or a fully frozen engine on Windows. Do not claim a working installer before
clean-machine tests. Initial shipping target: Windows x64, per-user installation.

Future policy interface: a held complete request is evaluated before upstream body
transmission. ALLOW forwards; BLOCK returns a documented synthetic error. This
interface is intentionally deferred: the current proxy permits all traffic.
Future enforcement requires bounded buffering, timeout handling, protocol coverage,
and bypass control. Response streaming needs explicit interoperability tests.

Tradeoffs: dependency footprint, Python/native packaging complexity, engine version
coupling. Reconsider a different engine if redistribution or compatibility testing
fails. Audit licenses and notices before publishing executable bundles.
